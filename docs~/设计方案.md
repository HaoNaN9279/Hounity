# Hounity 项目设计方案

## 一、项目定位与总体架构

Hounity 的目标是在 Unity 编辑器内构建一套**基于 GraphView 的节点化 HDA 工作流系统**，替代 Houdini Engine for Unity 的 Asset 管理方式，同时保留 Houdini Engine 核心作为底层执行引擎。与现有 Houdini Engine for Unity 最大的区别在于：现有插件中每个 HDA 是场景中一个独立的 GameObject，参数在 Inspector 中调整，Cook 结果直接输出到场景；而 Hounity 将 **HDA 视为工作流中的一个节点**，多个 HDA 节点和其他工具节点可以通过连线组合成完整的工作流，最终产物是离线资产（Mesh、Prefab、ScriptableObject 数据等），而非场景中的实时对象。

这一设计思路参考了 NodeGraphProcessor 的架构——一种基于 Unity UIElements 和 GraphView 的数据处理图框架，支持节点与图的序列化（ScriptableObject 存储）、依赖顺序执行以及自定义节点 API。

### 架构分层

```
┌─────────────────────────────────────────────────────────┐
│                     Editor UI Layer                       │
│  GraphView 编辑器 │ 节点 Inspector │ 多任务管理器面板    │
├─────────────────────────────────────────────────────────┤
│                   Workflow Engine Layer                   │
│  图序列化/反序列化 │ 依赖排序 │ 增量Cook调度 │ 缓存管理  │
├─────────────────────────────────────────────────────────┤
│                    Node System Layer                      │
│  HDA节点 │ 资源选择节点 │ GameObject选择节点 │ 预览节点 │
├─────────────────────────────────────────────────────────┤
│                 Houdini Bridge Layer                      │
│  HEU_HoudiniAsset 封装 │ HDA参数映射 │ 异步Cook管理     │
├─────────────────────────────────────────────────────────┤
│               Houdini Engine Core (External)              │
│              HAPI Session │ HDA Cook │ 几何输出           │
└─────────────────────────────────────────────────────────┘
```

Houdini Bridge Layer 直接复用 Houdini Engine for Unity 的公开 API。该插件提供了分层的编程接口：Asset 层（HEU_HoudiniAssetRoot、HEU_HoudiniAsset、HEU_ParameterUtility）适合简单的参数查询与修改；Utility 层（HEU_HAPIUtility、HEU_InputUtility、HEU_InputMeshUtility、HEU_SessionManager）适合构建复杂节点网络和动态工作流。Hounity 应该在这两层之上构建自己的节点封装，而不直接操作更底层的 HAPI 接口。


## 二、节点系统设计

### 2.1 节点数据模型

所有节点数据必须继承 `BaseNodeSO`（ScriptableObject），这是 Unity 编辑器序列化的基石。GraphView 本身不负责数据持久化，节点的端口状态、参数值、连接关系都需要通过 ScriptableObject 来保存和恢复。

节点数据模型分为三个层次：

**WorkflowGraphSO**（工作流根数据）包含节点列表、边列表和暴露的参数集。每个 Workflow 保存为一个独立的 ScriptableObject 资源，可被其他 Workflow 引用或嵌套。

**BaseNodeSO**（节点基类）包含节点唯一 ID、位置、暴露参数列表和执行状态。子类包括：
- `HDANodeSO`：封装一个 HDA 资产路径和参数映射表
- `AssetSelectorNodeSO`：资源选择节点的配置数据
- `GameObjectSelectorNodeSO`：GameObject 选择节点的配置数据
- `MeshToolNodeSO`：LOD/ShadowProxy/CollisionMesh 生成节点的配置
- `PreviewNodeSO`：预览节点的配置
- `OutputNodeSO`：输出节点的配置（指定输出路径和格式）

**PortSO**（端口数据）记录端口方向、容量（单连接/多连接）和数据类型。

### 2.2 节点类型与功能

**HDA 节点**是最核心的节点类型。每个 HDA 节点持有一个 HDA 文件路径，在初始化时通过 `HEU_HAPIUtility.InstantiateHDA` 加载 HDA 并创建 Houdini Engine 会话。节点的输入端口对应 HDA 的输入参数（如 objpath 类型的参数），输出端口则暴露 HDA 的输出几何。参数映射通过读取 HDA 的暴露参数列表，将其转换为 Unity Inspector 中可编辑的字段。

**资源选择器节点**支持两种模式：

- 单个资源选择：通过 `ObjectField` 直接指定一个 Unity 资源（Mesh、Texture、Prefab 等）。
- 多个资源选择：支持按命名规则过滤。命名过滤应支持 Contains、StartsWith、EndsWith 和 Regex 四种匹配模式，参考 Unity 内置 Search Provider 的文件搜索能力（该能力原生支持 regex 和 globs 模式匹配）。选择结果以列表形式输出到下游节点。

**GameObject 选择器节点**支持三种选择策略：

- 按父子级结构递归选择：从指定的根 GameObject 出发，递归遍历所有子对象。
- 按命名选择：对层级中 GameObject 名称进行模式匹配。
- 按组件及字段值选择：检查 GameObject 上是否挂载指定类型的组件，并可选地匹配组件字段的数值条件。Any Object Finder 等现有工具的实现思路可以参考——它支持对对象字段或成员进行递归的数值条件匹配，同时支持在数组和可序列化类实例中继续深入。

**Mesh 工具节点**包含三个子类型，后续章节单独展开。

**预览节点**接收上游的 Mesh 或几何数据，在节点图内嵌的 Preview 区域或独立的 Preview 窗口中渲染。使用 `PreviewRenderUtility` 实现轻量级预览，避免创建实际的场景对象。

**输出节点**是工作流的终点，将上游数据序列化为 Unity 离线资产。支持输出 Mesh、Prefab、ScriptableObject 和 JSON 等格式。


## 三、HDA 参数映射机制

### 3.1 参数类型映射

Houdini Engine 的参数通过 `HEU_ParameterData` 暴露，支持的参数类型包括 Int、Float、String、Toggle、Color、Vector（2/3/4）、Ramp 等。每种类型需要映射到对应的 Unity 编辑器字段：

| Houdini 参数类型 | Unity 编辑器控件 | C# 数据类型 |
|---|---|---|
| Int / Int Tuple | IntField / Vector2IntField | int / Vector2Int |
| Float / Float Tuple | FloatField / Vector3Field | float / Vector3 |
| String | TextField | string |
| Toggle | Toggle | bool |
| Color / Vector4 | ColorField | Color |
| Ramp | 自定义 RampField | AnimationCurve（近似映射） |
| File Path | 自定义 FilePathField | string |

参数读取使用 `HEU_ParameterAccessor.GetInt/GetFloat/GetString` 等方法，写入使用 `HEU_ParameterAccessor.SetInt/SetFloat/SetString`。

### 3.2 参数映射的持久化

HDA 节点在 GraphView 中创建时，会自动读取 HDA 的暴露参数列表，生成对应的 Unity 编辑器字段，并将用户设置的值序列化到 `HDANodeSO` 中。当下游节点重新 Cook 时，`HDANodeSO` 中缓存的参数值会被写回 HDA 再触发 Cook。这种设计避免了每次 Cook 都需要重新读取 HDA 参数定义的开销。

### 3.3 暴露参数（Exposed Parameters）

Workflow 级别支持暴露参数，允许外部脚本或 Inspector 在运行时修改 Workflow 的行为。这参考了 NodeGraphProcessor 的 Exposed Parameter 机制——参数值在图处理时更新，可从脚本或 Inspector 中设置。在 Hounity 中，暴露参数可以绑定到任意节点的任意参数上，形成 `Workflow → Node → Parameter` 的三级映射链路。


## 四、工作流引擎

### 4.1 图的序列化与反序列化

整个节点图持久化为 ScriptableObject 资源。序列化时遍历所有 `BaseNodeSO`，将其位置、参数和端口连接写入 `WorkflowGraphSO`。反序列化时重建 GraphView 的节点视图和边。

需要特别注意的是，GraphView 的 Port 如果设置为 Multi capacity（多连接），在 ScriptableObject 序列化时容易丢失连接数据。因此，端口连接关系不应依赖 GraphView 自身的序列化，而应在 `WorkflowGraphSO` 中维护独立的边列表，GraphView 重建时根据边列表恢复连接。

### 4.2 执行调度

工作流的执行遵循依赖顺序：从输出节点逆向遍历，收集所有上游节点的依赖关系，构建有向无环图（DAG），然后按拓扑排序依次执行每个节点的计算逻辑。NodeGraphProcessor 的 Graph Processor 正是采用了这种依赖顺序执行节点的逻辑。

执行时区分两种模式：

- **全量 Cook**：所有节点重新计算。适用于首次构建或大规模参数变更。
- **增量 Cook**：仅重新计算参数发生变化的节点及其下游节点。适用于迭代调整。

增量 Cook 的关键在于参数哈希：每个节点在执行后记录其输入参数的哈希值，下次执行前对比哈希，如果未变化则跳过。这一思路参考了 Houdini Engine 异步 Cook 的缓存机制——只有当输入参数变化超过某个阈值时才触发重新 Cook。

### 4.3 后台计算与主线程保护

“不卡 Unity 主线程”是本项目的核心需求之一。实现策略分为两个层面：

**Houdini Cook 层面**：Houdini Engine 支持异步 Cook。需要在初始化会话时设置 `hapi.initialize` 的异步模式，然后使用 `RequestCook` 时传入 `Async = true`，Cook 操作会在后台执行，不阻塞 Unity 主线程。Cook 完成后通过回调 `OnHoudiniAssetCookComplete` 通知。

**Unity 侧计算层面**：LOD 生成、碰撞体简化等纯 CPU 计算任务应使用 Unity 的 Job System 和 Burst Compiler。Job System 将小单元的工作调度到工作线程，利用所有 CPU 核心；Awaitable 类集成了 C# async/await 与 Unity 帧循环，使方法可以在不阻塞主线程的情况下挂起和恢复。

对于必须在主线程执行的操作（如创建 Mesh 对象、修改 GameObject 层级），应采用分帧策略：将大操作拆分为多个小步骤，在 `EditorApplication.update` 回调中逐帧执行。


## 五、Mesh 工具节点设计

### 5.1 Mesh 生成多级 LOD

LOD 生成节点接收上游的 Mesh，输出包含多个 LOD 级别的 Mesh 集合和对应的 LODGroup 配置数据。

实现方案采用**双路径策略**：

**路径 A — Unity 内置 LOD 生成器**：Unity 的 Mesh LOD 生成器在模型导入时运行，分析网格以确定要折叠的边和要保留的三角形，同时保持原始形状并避免视觉伪影。生成器在原始网格上执行第一轮迭代，后续每轮在前一轮的 LOD 网格上运行，每个后续 LOD 的索引数约为前一个的一半。原始网格至少需要 256 个三角形才能启动简化过程。Hounity 可以通过 `MeshUtility` 相关 API 在编辑器脚本中触发这一流程。

**路径 B — 自定义 QEM 简化**：对于需要更精细控制的情况（如保留 UV 边界、特定区域的细节权重），使用基于二次误差度量（QEM）的网格简化算法，在 Job System 中并行执行边折叠操作。

输出数据包括各级 LOD 的 Mesh、每级的屏幕相对高度（Screen Relative Transition Height）以及 LODGroup 组件配置。LOD 级别数和每级的目标三角形比例作为节点参数暴露。

### 5.2 Mesh 生成 ShadowProxy

ShadowProxy 是为远处物体生成的低面数阴影投射网格。参考 ShadowProxyMesh 的实践，LOD 网格 + CSM + ShadowProxyMesh 是最轻量的阴影组合方案。

生成流程：接收输入 Mesh → 使用 PolyReduce 逻辑进行大幅度简化（目标面数可低至原网格的 5%-10%）→ 移除内部不可见部分 → 输出简化的 ShadowProxy Mesh。Houdini 侧的 PolyReduce SOP 可以在 HDA 节点中完成简化，Hounity 的 ShadowProxy 节点则封装这一逻辑为独立的 Unity 侧工具节点，供非 Houdini 用户使用。

### 5.3 Mesh 生成 CollisionMesh

碰撞网格生成节点输出 Unity 的 Collider 配置。根据精度需求提供三个级别：

**凸包模式**：对输入 Mesh 计算凸包，生成单个 `MeshCollider` 并设置 `convex = true`。适用于简单物体。

**VHACD 分解模式**：使用 VHACD（体素化分层近似凸分解）算法将凹网格分解为多个凸包，生成复合 `MeshCollider`。Unity 生态中已有 Easy Collider Editor 等工具集成了 VHACD 凸包生成功能，只需点击一下即可在任何网格上自动生成多个凸包网格碰撞体。Hounity 可以内置 VHACD 库（或通过 Native Plugin 调用），在节点中暴露分解参数（体素分辨率、最大凸包数、精度等）。

**简化代理模式**：使用简化的 ShadowProxy 网格作为碰撞体。适用于不需要精确碰撞但需要基本形状近似的场景。


## 六、多任务管理器

多任务管理器负责协调多个工作流的并行执行和 Houdini Engine 会话的管理。

**会话管理**：Houdini Engine 的 Session 是有限资源（通常受许可证限制）。多任务管理器需要维护一个 Session 池，按需分配和回收。使用 `HEU_SessionManager` 创建和管理会话，并通过 `HEU_SessionHAPI` 包装器与会话交互。

**任务队列**：每个工作流执行作为一个 Task 提交到队列中。Task 包含工作流引用、执行状态（Pending / Cooking / PostProcessing / Completed / Failed）和进度信息。管理器按优先级和依赖关系调度 Task，Houdini Cook 任务和 Unity 侧后处理任务分属不同的队列。

**进度与取消**：每个 Task 提供进度百分比和当前阶段的文本描述。Cook 过程中可以通过 HAPI 的取消机制终止任务。多任务管理面板以列表或卡片形式展示所有活跃任务及其状态。

**编辑器集成**：多任务管理器作为独立的 EditorWindow 存在，也可以通过 GraphView 编辑器底部的状态栏快速访问。使用 `EditorApplication.update` 驱动任务队列的轮询和进度更新。


## 七、资源管理

Unity 内资源管理模块负责工作流涉及的各类资源的加载、引用和生命周期管理。

**资源引用方式**：所有资源引用使用 Unity 的 `AssetDatabase` GUID 系统，确保资源移动或重命名后引用不会断裂。在 ScriptableObject 中，资源引用通过 `UnityEngine.Object` 字段直接序列化。

**资源缓存**：HDA 的 Cook 输出（Mesh、材质、纹理等）缓存到磁盘的临时目录中，工作流执行时优先读取缓存，仅在参数变化时重新 Cook。缓存以 HDA 文件路径 + 参数哈希作为键值。

**资源回收**：工作流删除时，其产生的临时资源应被清理。使用 `EditorUtility.UnloadUnusedAssetsImmediate` 或自定义的引用计数机制进行资源回收。对于输出到 `Assets/` 目录的离线资产，由用户自行决定是否保留。


## 八、节点需求实现细节

### 8.1 资源选择器节点

**单个资源选择**：节点面板上提供一个 `ObjectField`，支持拖拽或点击选择。资源类型通过节点的输出端口类型约束（如 Mesh、Texture2D、Material）。

**多个资源选择 — 按命名选择**：提供一个根目录（`DefaultAsset` 类型的文件夹引用）、一个匹配模式（Contains / StartsWith / EndsWith / Regex）和一个模式字符串。节点执行时，通过 `AssetDatabase.FindAssets` 在指定目录下搜索符合条件的资源。结果以 `List<Object>` 输出到下游。参考 Unity 的 Files Search Provider，它原生支持 regex 和 globs 模式匹配。

### 8.2 GameObject 选择器节点

**按父子级递归选择**：节点面板提供一个根 GameObject 引用和最大递归深度参数。执行时使用 `Transform.GetComponentsInChildren` 或手动递归遍历获取所有子对象。

**按命名选择**：在递归选择的基础上增加名称过滤条件，支持 Contains / StartsWith / EndsWith / Regex。

**按组件及字段值选择**：指定组件类型（通过 `Type` 下拉框或拖拽脚本组件），并可选地设置字段过滤条件。字段过滤的实现方式参考 Any Object Finder：递归检查对象的字段或成员是否匹配数值条件，支持在数组和可序列化类中继续深入。字段过滤条件以字符串形式表达（如 `health > 50`），在节点中解析后应用。

### 8.3 模型预览器节点

预览节点接收上游的 Mesh 数据，在节点内部或独立的预览窗口中渲染。使用 `PreviewRenderUtility` 创建离屏渲染环境，通过 `Graphics.DrawMeshNow` 绘制网格。预览窗口支持鼠标旋转、缩放和平移。预览的材质使用默认的 Standard Shader 或 Wireframe Shader。

预览节点不参与工作流的输出，仅作为中间检查点使用。它有一个输入端口（Mesh）和一个直通输出端口（将输入 Mesh 原样传递到下游），这样可以将其插入任意 Mesh 数据流中而不影响工作流的完整性。


## 九、关键技术风险与应对

**Houdini Session 的线程安全**：HAPI 的 Session 调用本质上不是线程安全的。所有 HAPI 调用必须在同一个线程（通常是主线程）上序列化执行。异步 Cook 通过 `Async = true` 将 Cook 任务推送到 Houdini 引擎的后台进程，但请求的发起和结果的接收仍需在主线程完成。多任务管理器需要实现一个 HAPI 调用队列，确保同一 Session 上的请求按顺序执行。

**GraphView 在 Unity 2022.3 中的稳定性**：Unity 的 GraphView 是 Experimental 命名空间下的 API，在版本升级时可能发生变化。建议对 GraphView 的使用进行封装，将所有对 `UnityEditor.Experimental.GraphView` 的引用集中在一个适配层中，便于未来迁移到 Unity 的 Graph Toolkit（Unity 6.2 已引入）。

**大规模节点图的性能**：当工作流包含大量节点时，GraphView 的渲染和 ScriptableObject 的序列化可能成为瓶颈。应对策略包括：节点视图的懒加载（仅在可视区域内创建 VisualElement）、序列化时使用增量保存（仅序列化变更的部分）、以及将大型 HDA 输出数据进行外部文件存储而非嵌入 ScriptableObject。


## 十、实施路线建议

**阶段一（基础框架）** ：搭建 GraphView 编辑器窗口、BaseNodeSO 数据模型和 WorkflowGraphSO 序列化系统。实现最基本的 HDA 节点和输出节点，完成 HDA 参数读取、Cook 调用和输出资产生成的完整链路。

**阶段二（核心节点）** ：实现资源选择器节点、GameObject 选择器节点和模型预览节点。接入 Unity Job System 实现后台计算。实现多任务管理器的基本队列和进度显示。

**阶段三（Mesh 工具）** ：实现 LOD 生成、ShadowProxy 生成和 CollisionMesh 生成三个 Mesh 工具节点。LOD 优先使用 Unity 内置生成器，CollisionMesh 集成 VHACD 库。

**阶段四（优化与交付）** ：实现增量 Cook 的缓存机制、暴露参数系统和 Workflow 嵌套引用。完善多任务管理器的并发调度和取消机制。完成文档和示例工作流。
